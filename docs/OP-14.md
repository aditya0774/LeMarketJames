# OP-14: Buy order integration

The authenticated dashboard trade dialog submits a market BUY to `POST /api/v1/orders`.
The backend authorizes the account, checks tradability, captures the current market ask
price through `MarketDataService`, validates cash, and commits a `SUBMITTED` order.
The dialog confirms the returned identifier/status and refreshes the dashboard orders.
Existing `/orders` bookmarks redirect to the dashboard.

The saved price is a submission snapshot, not an execution price. This story does not
reserve cash, fill orders, or change cash/holdings. Several open orders can therefore
exceed the current cash in aggregate; reservation rules belong to the order lifecycle.
The existing order schema supports this flow without a migration. Pricing depends on
the read-only market interface rather than simulator internals.

## Verification

- Frontend: `cd apps/frontend`, then `npm test -- --watch=false` and `npm run build`.
- Backend: from the repository root, run `mvn -B test`.
- PostgreSQL: start a **disposable**, migrated PostgreSQL database, then run
  `mvn -B -pl services/core-service -am -Dspring.profiles.active=postgres-test "-Dtest=OwnDataIntegrationTest,BuyOrderIntegrationTest" -Dsurefire.failIfNoSpecifiedTests=false test`.
  Configure `TEST_DATABASE_URL`, `TEST_DATABASE_USER`, and `DB_PASSWORD` when needed.
  The profile validates the existing schema and does not run H2 seed scripts.
- Jenkins starts its disposable PostgreSQL service and runs the integration tests before
  building versioned images. After starting the stack, `bash scripts/verify-buy-order.sh`
  submits through the frontend proxy, checks PostgreSQL, restarts core-service, and compares
  the persisted order with its original response. The script requires Bash, Node, curl,
  and Docker Compose on the Jenkins agent.

`BuyOrderIntegrationTest` seeds shared account data and uses the auth service's JWT format.
It mocks remote market pricing and exercises the real controller, service, and repositories. It deliberately has no enclosing test transaction: a separate database
read and subsequent HTTP request must observe the committed record. It deletes only its
own test users and orders afterward.

## Browser acceptance check

1. Sign in to an account with cash and open a tradable stock from the dashboard.
2. Submit a BUY for one share. While pending, verify the submit button is disabled.
3. Verify the confirmation contains the returned order ID and `submitted` status, and
   that the dashboard order list shows the new order.
4. Submit a quantity whose cost exceeds the account cash. Verify a readable error and
   no new order. Verify non-tradable stocks cannot be submitted.
5. Reload the dashboard and verify the submitted order remains present.

The API smoke test exercises the frontend proxy but does not automate browser clicks;
the browser acceptance check and live Jenkins run remain necessary before story sign-off.
